# 畅行租车 AI Agent —— 源码逐文件·逐方法讲解

> 目标：让你在没看过代码的前提下，快速看懂每个文件、每个方法到底在干什么、为什么这么写，并能在面试里讲清楚。
> 配套背景：项目 =「Python AI 客服 Agent（本仓库）」+「Spring Cloud 后端微服务（本仓库之外）」。本文只讲本仓库。

---

## 0. 一句话看懂这个项目

这是一个**租车平台的智能客服 Agent 后端**，用 **Python + FastAPI** 实现。它的工作方式是：

```
用户在前端问一句话
   → 判断用户意图（想查车 / 查门店 / 查订单 / 查评价 / 闲聊）
   → 按意图调用后端 Spring Cloud 的 HTTP 接口，拿到真实业务数据
   → 把真实数据拼进 Prompt，再调用大模型（LLM）生成一句自然中文回复
   → 通过 SSE 流式打字机效果返回给前端
```

第二版优化（本仓库现状）在原来的基础上加了三件事：

1. **LangChain 框架**：不再直接调 OpenAI SDK，改用 LangChain 的 `ChatOpenAI`、消息对象、Prompt 模板；
2. **RAG**：把「高频常见问题」建成向量知识库，用户问题命中相似问答时直接复用答案，省掉一次 LLM 调用；
3. **高并发优化**：LLM 出口限流、SSE 连接数限流、会话上下文瘦身、业务数据短缓存。

## 2. config.py —— 配置中心

**职责**：在最开始执行 `load_dotenv()` 读 `.env` 文件，然后把每个环境变量读成一个个 Python 常量，供整个项目引用。所有配置都有默认值，`.env` 里可以不填。

逐项说明（按功能分组）：

**Agent 服务**
- `AGENT_PORT`：本服务监听端口，默认 5000。
- `BACKEND_API_URL`：后端 Spring Cloud 网关地址，Agent 查数据都往这里发请求。

**LLM 配置**
- `OPENAI_API_KEY`：LLM 的 Key；本地 Ollama 填 "ollama" 即可。
- `OPENAI_BASE_URL`：LLM 接口地址；本地 Ollama 默认 `http://localhost:11434/v1`。
- `OPENAI_MODEL`：模型名，默认 `qwen:1.8b`。
- `OPENAI_TEMPERATURE` / `OPENAI_MAX_TOKENS`：温度（随机性）和最大生成长度。

**RAG / 知识库**
- `EMBEDDING_MODE`：嵌入后端，`hash`（离线零依赖）或 `ollama`。
- `EMBEDDING_DIM`：向量维度，默认 512。
- `OLLAMA_EMBED_BASE_URL` / `OLLAMA_EMBED_MODEL`：Ollama 嵌入服务地址和模型。
- `FAQ_KB_PATH`：可选的额外 FAQ JSON 文件路径。
- `FAQ_LEARNED_PATH`：运行中学习到的问答的落盘路径。
- `RAG_TOP_K`：检索返回前 K 条。
- `RAG_SIMILARITY_THRESHOLD`：相似度 ≥ 该值就直接复用已有答案（不调 LLM）。
- `RAG_CONTEXT_THRESHOLD`：相似度在该值和复用阈值之间时，作为参考上下文注入 Prompt。
- `FAQ_MAX_LEARNED`：学习到的问答最多保留条数。

**缓存**
- `FAQ_CACHE_TTL`：高频答案缓存存活秒数。
- `DATA_CACHE_TTL` / `DATA_CACHE_MAX`：业务数据缓存的存活秒数和最大条数。

**并发限流**
- `LLM_MAX_CONCURRENCY`：同时进行的 LLM 调用上限。
- `LLM_QUEUE_MAX`：等待排队的上限，超过就快速失败。
- `MAX_HISTORY_MESSAGES`：会话上下文只保留最近 N 条历史。
- `SSE_MAX_TOTAL` / `SSE_MAX_PER_USER`：SSE 长连接的全局上限和单用户上限。

**CORS**：`CORS_ORIGINS` 允许哪些前端域名跨域访问。

> 面试要点：能说出「哪些参数是管并发的」——LLM_MAX_CONCURRENCY/LLM_QUEUE_MAX/SSE_*，说明你不是只会用默认值。

## 3. models.py —— 数据模型

用 Pydantic 定义接口入参/出参，FastAPI 会自动校验请求体类型。

- **ChatRequest**（聊天请求入参）：
  - `conversation_id`：会话 ID，用于拉取历史上下文；
  - `content`：用户这句话的文本；
  - `car_id` / `car_name`：可选，用户当前正在看的车（用于上下文感知，让回答更贴题）；
  - `token`：可选，用户登录 JWT，查订单/个人信息这类需要鉴权的接口才用得上。
- **ChatDelta**（流式增量格式）：`type`（start/delta/done/error）、`content`、`message_id`、`error`。实际上 main.py 里的 SSE 直接用了字典，这个类保留作为协议说明。
- **FAQItem**：`question` + `answer`，用于 `/rag/faq` 接口动态往知识库追加标准问答。

## 4. tools.py —— 意图识别 + 数据查询（信息最密集、面试必看）

这个文件是「大脑的判断 + 动手查数据」两层。

### 4.1 模块级「规则字典/正则」

- `BRAND_KEYWORDS`：品牌 → 该品牌下所有车型关键词的大字典（大众→朗逸/宝来/迈腾…，宝马→3系/X3…）。用于识别用户提到的品牌。
- `CAR_TYPE_KEYWORDS`：车类型词 → 后端 `type` 字段值（如「轿车」→ `sedan`，「SUV」→ `suv`）。
- `CITY_PATTERN`：一个覆盖主要城市的正则，用于识别「北京门店」「成都取车」里的城市。
- `TRIM_NAME_PATTERN`：常见车型名正则，用于从「朗逸多少钱」里提取「朗逸」做精确查询。

> 面试要点：这 4 个是典型的**规则型意图识别**（关键词+正则），不是机器学习。优点是零成本、可控、可解释；缺点是覆盖面靠人肉维护。

### 4.2 class DataService —— 数据桥梁

它内部维护一个 `httpx.AsyncClient`（异步 HTTP 连接池），对外提供「意图识别 → 数据获取 → 格式化成文本」的完整能力。

**`__init__(self, base_url)`**
- 保存后端网关地址，并创建一个超时 15 秒的异步 HTTP 客户端，复用连接池提高性能。

**`detect_intent(self, message) -> tuple[str, dict]`**
- 意图识别核心。按**优先级从上到下**匹配，命中即返回 `(意图标识, 参数字典)`。
- 顺序依次是：用户订单 → 用户信息 → 车辆评价 → 带城市门店 → 门店 → 品牌/车型 → 车辆类型 → 热门排行 → 通用浏览 → 单独价格 → 兜底 `none`。
- 每个意图内部还会顺带提取参数：比如「朗逸多少钱」既命中品牌，又命中价格词，就返回 `car_detail` + `keyword=朗逸`。
- 返回 `none` 表示没识别出来，交给 LLM 自由回答。

**`fetch_data(self, intent, params, token) -> Optional[str]`**
- 数据获取路由：根据 `intent` 分发到下面对应的 `_xxx` 方法，并统一捕获异常（异常返回 None，不让查数据失败拖垮整轮对话）。
- 返回的是**已经格式化好的文本**，直接拼进 Prompt 给 LLM 看。

**`_search_cars(self, params)`**
- 查车辆列表：调后端 `GET /cars` 拿所有有库存的车，在内存里按品牌名或车型类型再过滤，最多取前 10 辆，格式化成「名称｜日租金｜类型｜座位｜燃料｜变速箱｜状态」的文本。

**`_get_car_detail(self, params)`**
- 查单车详情：先从列表接口模糊匹配车型名，再调 `GET /cars/{id}` 拿完整参数，组装成品牌/类型/租金/座位/燃料/变速箱/马力/排量/扭矩/尺寸/配置 等一行行文本。

**`_get_stores(self, params)`**
- 查门店：调 `GET /stores`，按城市过滤（城市名出现在 city 或 address 字段），最多展示 5 家，输出名称/地址/电话/营业时间。

**`_get_user_bookings(self, token)`**
- 查订单（需登录）：没 token 就返回「需要登录」提示；有 token 就带 `Authorization: Bearer` 调 `GET /bookings`，把订单状态（pending/confirmed/active/completed/cancelled 映射成中文）、日期、金额、取还车地格式化成文本。

**`_get_user_profile(self, token)`**
- 查个人信息（需登录）：带 token 调 `GET /user/profile`，输出姓名/手机号/会员等级/账户状态。

**`_get_car_reviews(self, params)`**
- 查车型评价：先按车型名模糊匹配到车，再调 `GET /reviews/trim/{id}` 拿评价，输出用户名+星级+租期+评价内容（最多 5 条）。

**`_get_hot_cars(self)`**
- 查热门排行：调 `GET /cars/hot`，把「基于真实成交数据」的排行按第 1/2/3/4 名输出，含价格、座位、燃料、成交单数。

**`query(self, message, token)`**
- **对外统一入口**：先 `detect_intent`，如果是 `none` 返回 None，否则 `fetch_data`。`agent.py` 就是调它。

**`close(self)`**
- 关闭 HTTP 连接池，释放网络资源（应用关闭时调用）。

## 5. embeddings.py —— 文本向量化

RAG 要「相似度检索」，前提是把文字变成数学向量。这个文件负责这件事。

- **`_normalize(vec)`**：把一个向量 L2 归一化（长度变成 1），保证后续用「点积」就能得到余弦相似度。
- **`_fit_dim(vec, dim)`**：把任意长度向量折叠到指定维度（按位置模运算叠加再归一化）。作用：不管 Ollama 嵌入模型返回多少维，都统一到 `EMBEDDING_DIM`，让检索层维度一致。
- **`hash_embed(text, dim)`**：**默认的确定性嵌入**。把文本切成 1/2/3 字 n-gram，每个 gram 用 md5 哈希映射到一个桶累加计数，再归一化。纯本地、零依赖、可复现。
- **class EmbeddingProvider**：
  - `embed_query(text)`：给「一条查询」出向量（给用户问题用）。
  - `embed_documents(texts)`：给「一批文档」出向量（建库用）。
  - `_embed(text)`：真正干活的地方——`EMBEDDING_MODE=ollama` 时优先调 Ollama，失败就降级回 hash。
  - `_ollama_embed(text)`：用 httpx 调 Ollama 的 `/api/embeddings`，拿不到就返回 None 触发降级。
- `embedding_provider`：模块级单例，全项目共用同一个嵌入器。

> 面试要点：默认 hash 嵌入是「离线、零依赖」的工程取舍；想更强语义切 Ollama。这体现你知道「嵌入后端可替换」的抽象设计。

## 6. cache.py —— 轻量缓存

- **`TTLCache(max_size, ttl)`**：一个带过期时间的 LRU 缓存。
  - `__init__`：约定容量和默认 TTL。
  - `get(key)`：先删过期项，命中则把该项移到队尾（标记最近使用）并返回；否则返回 None。
  - `set(key, value, ttl)`：写入并更新过期时间，容量超了从最久未用开始淘汰。
  - `_evict()`：内部清理所有已过期项。
  - `__len__`：当前条目数。

> 面试要点：这是「自己写的小缓存」，避免为这点需求引入 Redis/第三方库。能说清「TTL 管过期 + LRU 管容量」就够。

## 7. limits.py —— 并发与连接限流（高并发核心）

- **`RateLimitedError`**：自定义异常，表示「触发限流」，用于快速失败。

- **class LLMLimiter**（LLM 出口限流）：
  - `__init__(max_concurrency, queue_max)`：核心是一个 `asyncio.Semaphore`（信号量）+ 一个等待计数。
  - `__aenter__`：进入时先判断「等待人数是否已达 queue_max」，到顶就抛 `RateLimitedError`（快速失败，不无限排队）；否则 +1 等待数，然后 `await acquire()` 真正拿到并发额度，+1 活跃数。
  - `__aexit__`：释放信号量，-1 活跃数。
  - `active` / `waiting`：只读属性，暴露当前活跃和等待数（给 /health 展示）。
  - 配合 `async with llm_limiter:` 使用，保证一段 LLM 调用全程占用并发额度。

- **class SSEConnectionLimiter**（SSE 长连接限流）：
  - `try_acquire(user_key)`：超过全局上限或单用户上限就返回 False（拒绝），否则 +1 计数并返回 True。
  - `release(user_key)`：连接结束时 -1。
  - `total`：当前连接总数。

> 面试要点：
> 「LLM 为什么限流」——LLM 调用慢、贵、有配额，高峰要削峰；信号量控制并发，queue_max 控制排队长度，满了直接 429 快速失败，保护 LLM API。
> 「SSE 为什么限流」——SSE 是长连接，恶意/突发会占满连接资源，所以要限制全局数 + 单用户数。

## 8. rag.py —— RAG 知识库（LangChain + 向量检索）

这是「使用 LangChain + RAG」落地的核心文件，面试重点。

### 8.1 数据结构和工具

- **`Hit`**（dataclass）：一次检索命中的结果，含 `question / answer / score / doc` 四个字段。
- **`_cosine_sim(query, matrix)`**：计算 query 向量与 matrix 每一行（都已归一化）的余弦相似度，向量化一次算完。

### 8.2 class FAQRetriever(BaseRetriever) —— LangChain Retriever 封装

- 继承 LangChain 的 `BaseRetriever`，用 `_store`（Pydantic PrivateAttr）持有底层 `RAGStore`。
- **`_get_relevant_documents(query)`**：同步检索，返回 `Document` 列表（LangChain 标准 `invoke` 走这里）。
- **`_aget_relevant_documents(query)`**：异步检索，返回 `Document` 列表（`ainvoke` 走这里）。

> 面试要点：这就是「把自研向量库接入 LangChain 标准 Retriever 协议」——重写 `_get_relevant_documents` / `_aget_relevant_documents`，就能被 LangChain 的任何链条/Agent 当 retriever 用。

### 8.3 class RAGStore —— 向量检索核心

- `__init__`：初始化 `_docs`（文档列表）、`_vectors`（向量矩阵）、`_learned`（学习到的问答），然后 `_load()`。
- `_load()`：从 `faq_data.SEED_FAQS` + 可选外部 JSON + 上次落盘的「已学习问答」三处把文档加载进来。
- `_to_doc(item)`（静态）：把 `{question, answer}` 转成 LangChain `Document`（answer 放 page_content，question 放 metadata）。
- `ensure_built()`：懒加载地给所有文档向量化，只建一次索引（双检锁思想，避免重复建）。
- `search(query, top_k)`：异步检索。先把问题向量化，再算相似度、倒序取 top_k，返回 `Hit` 列表。
- `search_sync(query, top_k)`：同步版（供 Retriever 的同步 invoke 调用），用 hash 嵌入。
- `_rank(q, top_k)`：真正的「向量对比 + 排序」步骤。
- `remember(question, answer, force)`：把一轮新问答**学习进知识库**。force=False 时会先做「长度过滤 + 相似度去重」（太短或已存在就不存）；然后向量化新问题、追加进矩阵、写入 `_learned` 并落盘。
- `_persist_learned()`：把已学习问答写回 JSON 文件（重启不丢）。
- `learned` / `docs`（property）：暴露学习列表和全部文档。

### 8.4 class RAGService —— 对外门面（agent 只跟它打交道）

- `__init__`：组装 `RAGStore` + `FAQRetriever`，并建一个 `TTLCache` 答案缓存。
- `ensure_built()`：透传建索引。
- **`answer_from_cache(question)`**（核心方法①）：先查进程内答案缓存，再向量检索 top1——相似度 ≥ 阈值就直接返回标准答案（**这一分支完全不调 LLM**）。这是「高频问题缓存 + 相似问复用」的实现。
- **`retrieve_context(question)`**（核心方法②）：相似度没到复用阈值、但 >= 上下文阈值的那批 FAQ，作为参考知识注入 Prompt。
- `remember(question, answer, force)`：学习记忆。
- `all_items()`：返回知识库全部条目（给管理接口展示）。
- `persist()` / `stats()`：落盘 / 返回规模统计。

- `rag_service`：模块级单例。

> 面试要点（RAG 讲法）：
> 一次问答有两条路——(1) 命中了高频/相似问题，直接复用答案，省 LLM 调用；(2) 没命中，就把检索到的相关知识塞进 Prompt，让 LLM 基于知识作答（标准 RAG 的「检索增强」）。检索用向量余弦相似度，文档用 LangChain `Document` + `BaseRetriever` 承载。

## 9. agent.py —— 核心编排（LangChain）

- `NO_CACHE_INTENTS = {"user_bookings", "user_profile"}`：需要鉴权的个性化数据不做短缓存（避免串号/过期）。

- **class AgentService**：
  - `_PROMPT`（类属性）：LangChain `ChatPromptTemplate`，三段式：system 指令 → 历史消息占位符 → 用户输入。
  - `__init__`：初始化 LangChain `ChatOpenAI`（LLM）、后端 httpx 客户端、`DataService`、`LLMLimiter`、`TTLCache`（业务数据缓存）。
  - **`_prepare(req)`**（核心方法）：一轮对话的「预处理」，返回 `(消息列表, 命中缓存答案)`：
    1. 先问 RAG `answer_from_cache`，命中就直接返回缓存答案（消息列表空、不调 LLM）；
    2. 没命中 → 意图识别+查数据（`_data_context`）；
    3. 再检索 RAG 补充知识上下文；
    4. 历史消息瘦身（只留最近 N 条）；
    5. 拼 system + 历史 + 输入，产出 LangChain 消息列表。
  - **`_data_context(req)`**：意图识别+数据查询，读多写少的公共数据（车列表/门店等）做短缓存，鉴权类数据直接查不缓存。
  - **`get_conversation_history(conversation_id)`**：调后端 `/service/conversations/{id}` 拉历史，把 `sender` 映射成 LangChain 的 `HumanMessage`/`AIMessage`；失败静默返回空列表。
  - **`build_system_prompt(req, data_context, rag_context)`**：拼 system 指令 = 角色设定 + 车辆上下文 + 真实业务数据 + RAG 知识，并强调「基于数据回答、别编造」。
  - **`chat(req)`**：非流式。`_prepare` 命中缓存直接回；否则 `async with llm_limiter:` 里 `ainvoke`，拿答案后 `rag_service.remember` 记忆，返回。
  - **`chat_stream(req)`**：流式。命中缓存就一次性 yield 整段答案；否则在限流器内 `astream` 逐 token yield，结束后把完整答案交给 RAG 记忆。
  - **`_extract(message)`**（静态）：从 LangChain 消息里稳健地提取纯文本（兼容 str 或内容块列表）。
- `agent_service`：模块级单例。

> 面试要点：`_prepare` 是整个流程的「调度中心」，能顺着它讲清楚「RAG 命中→短路返回 / 未命中→查数据→注入知识→LLM」两条路径，是加分项。

## 10. main.py —— FastAPI 入口

- `sse_limiter`：全局 SSE 连接限流器（模块级单例）。
- **`lifespan(app)`**：FastAPI 生命周期。启动时打印地址 + **预热 RAG 索引**；关闭时优雅关闭两个 http 客户端、落盘 RAG。
- **`app`**：FastAPI 实例 + CORS 中间件。
- **`health()`**：`GET /health` 健康检查，额外返回 LLM 活跃/等待数、SSE 连接数、RAG 规模（方便观测运行状态）。
- **`hot_cars()`**：`GET /hot-cars` 代理转发后端热门车型。
- **`chat(req)`**：`POST /chat` 普通聊天，返回完整文本。
- **`chat_stream(req)`**：`POST /chat/stream` 流式聊天。先 `try_acquire` 拿连接额度，超限直接 429；否则进入事件生成器，`start`→逐条 `delta`→`done`，出错发 `error`，`finally` 释放连接额度。
- **`list_faq()`**：`GET /rag/faq` 查看知识库全部条目。
- **`add_faq(item)`**：`POST /rag/faq` 往知识库动态追加标准问答（运营可无代码扩容 FAQ）。
- **`__main__`**：`uvicorn.run` 启动，`reload=True` 便于开发热重载。

## 13. 一次请求的完整调用链（面试「讲全流程」用）

以用户问「怎么取消订单」为例（**RAG 命中路径**）：

1. `main.py /chat` 收到 `ChatRequest`
2. `agent.chat()` → `_prepare()`
3. `rag.answer_from_cache("怎么取消订单")` → 向量检索命中种子 FAQ → **直接返回标准答案，省掉 LLM**
4. `_prepare` 返回 `(空消息, 缓存答案)`，`chat` 直接返回

以用户问「上海有哪些大众的车」（**查数据 + LLM 路径**）：

1. `_prepare` → RAG 未命中
2. `_data_context` → `detect_intent` 识别出 `search_cars` + `brand=大众` → `fetch_data` 调后端 `/cars` → 过滤出大众车型文本
3. `retrieve_context` 检索 RAG 补充相关知识
4. 历史瘦身 + `build_system_prompt` 拼指令
5. `async with llm_limiter:` 内调 `llm.ainvoke` → LLM 基于真实数据生成回复
6. `remember` 把这轮问答学习进知识库（可选）

## 14. 面试常见追问速查（结合本项目）

1. **你的 RAG 怎么做的？** 见 §8：`Document`+`BaseRetriever` 承载，向量余弦相似度检索；命中阈值直接复用答案，否则注入 Prompt 增强生成。
2. **怎么减少重复调用 LLM？** 高频问题内存缓存 + 相似问复用，命中即短路。
3. **LLM 高峰怎么抗？** `LLMLimiter` 信号量限并发 + `queue_max` 快速失败。
4. **SSE 长连接怎么防滥用？** `SSEConnectionLimiter` 全局 + 单用户数限制，超限 429。
5. **长对话 token 膨胀怎么办？** `MAX_HISTORY_MESSAGES` 只取最近 N 条。
6. **意图识别怎么做的？** 规则型（关键词+正则），见 `tools.py`，可解释、零成本。
