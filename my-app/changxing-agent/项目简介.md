# 项目简介（面试版）

## 一句话版（约 15 秒开场）

> 我做的是一个**租车平台的智能客服后端**，用 Python + FastAPI 实现。核心链路是「识别用户意图 → 调后端查真实数据 → 拼 Prompt → 调大模型生成回复」，并通过 **LangChain** 编排大模型、**RAG** 做高频问题缓存，还针对高并发做了 **LLM 限流、SSE 连接限流**等优化。

---

## 完整版（约 1～2 分钟）

**项目背景**
租车平台客服咨询量大，需要一套 AI 客服来自动回答车辆、门店、订单、评价等常见问题，替代部分人工。

**我的工作内容**
1. 用 FastAPI 搭建对话接口：普通聊天 `/chat` + SSE 流式 `/chat/stream`；
2. 规则型意图识别 + 调用后端 Spring Cloud 接口聚合真实数据，把数据拼进 Prompt，避免大模型瞎编；
3. 用 LangChain 做 LLM 编排（ChatOpenAI、消息对象、Prompt 模板、BaseRetriever）；
4. 用 RAG 把高频 FAQ 建成向量知识库：命中相似问直接复用答案，少调一次大模型；
5. 高并发优化：LLM 出口信号量限流 + 排队上限快速失败、SSE 长连接限流、会话上下文瘦身、业务数据短缓存。

**技术栈**
Python、FastAPI、LangChain、RAG（向量检索）、SSE、httpx、Pydantic；对接 Spring Cloud 微服务。

---

## 3 个必讲的亮点

| 亮点 | 一句话讲法 |
|------|-----------|
| RAG 语义缓存 | 高频/相似问题命中知识库就直接返回答案，**短路不调大模型**，既降延迟又降成本 |
| LLM 出口限流 | 用 `asyncio.Semaphore` 控制并发 + 排队上限快速失败，**保护大模型 API 不被高峰打爆** |
| 规则 + 大模型混合 | 意图识别用规则（可解释、零成本、好维护），大模型负责自然语言生成，**各取所长** |

---

## 可能被追问的应对

- **为什么意图识别用规则而不是模型？**
  可解释、可控、零成本、覆盖当前业务场景够用；如果后续问题复杂了，可以再升级成模型分类或向量意图。

- **你的 RAG 具体怎么检索的？**
  把问题向量化后做余弦相似度，分两档：相似度高的直接复用答案，中等的作为上下文注入 Prompt 增强生成。

- **怎么应对高并发？**
  大模型调用慢且贵，所以：信号量限并发、队列上限快速失败、SSE 按单用户和全局限连接数、上下文只保留最近 N 条、公共数据做短缓存。
